# 手机语音方向：主入口收敛计划

日期：2026-11-25  
状态：方向计划；本轮只完成低风险对齐，不代表以下各项已排期实现。

## 出发点

手机是 Luna Bot 未来的主要使用入口。语音架构的主干保持不变：电脑或 Cloud 持有全部密钥，手机只走 companion 暴露的窄接口；通话继续分为「轮流说话」和「Live」两种。本轮已补齐的底层事实：

- Android 能正确识别并展示豆包·火山、千问两种语音引擎。
- Windows / Linux 的「轮流说话」不再只认 Fish Audio；已配置的豆包或千问语音凭证也能作为服务端转写凭证。
- companion 放开了一个精确形状的窄写口：手机只能把 `tts.provider` 切换为合法语音引擎，不能写 API key、Chatterbox 地址或其它配置。
- Android 设置页移除必然失败的语音密钥输入；密钥、Chatterbox 地址和实时通话凭证明确只在电脑端管理。

## 当前平台矩阵

| 能力 | 桌面 | Android |
| --- | --- | --- |
| 轮流说话 | macOS 端侧识别；Windows / Linux 走服务端转写 | 系统 SpeechRecognizer + 电脑 TTS |
| Live · OpenAI / Azure | WebRTC | 不支持 WebRTC，回退轮流说话 |

## 后续方向

### P1：统一「语音消息」语义

现状：入口叫「语音消息」，但只要能转写出文字，实际只发送文字；识别关闭或失败时才发送音频。技术上省一次机器人侧转写，产品语义却容易误解。

目标：把入口拆清或改名。建议优先改成「语音输入」，默认发送文字；保留长按或显式选项发送真正语音条。在线转写不可用时给出一次明确降级提示，而不是静默变成音频。

验证目标：用手机分别覆盖「识别成功只发文字」「用户选择发送音频」「电脑在线转写失败后的提示与降级」三条路径。

### P1：明确 `speakReplies` 在手机上的语义

现状：自动朗读的实际播放实现主要在电脑 renderer；手机普通聊天里没有同等独立的自动朗读播放器。手机上的开关更像修改机器人全局偏好，不像控制本机播放。

目标：先决定语义是「机器人回复应生成/播放语音」还是「当前设备朗读回复」。若手机是主入口，应实现手机本地自动播放队列，并把开关命名成设备语义或服务端偏好语义之一，不能继续混用。

验证目标：同一机器人分别在电脑在线、电脑不在线、手机前台三种状态下验证自动朗读行为与设置文案一致。

### P2：统一手机两套语音识别体系

现状：语音消息卡使用 Sherpa 端侧模型或电脑在线转写；轮流说话使用 Android 系统 SpeechRecognizer。三者识别质量、离线能力、隐私路径和语言支持都不同。

目标：形成一个识别路由层。短期先统一设置文案与隐私说明；中期评估是否让轮流说话也复用语音消息卡的 Sherpa / 服务端转写路径，或明确系统识别是通话专用、低延迟优先的独立选择。

验证目标：同一中文句式在语音输入与轮流说话中表现一致，或差异由文档和设计明确解释。

### P2：Android WebRTC Live

现状：Android 只实现千问 / 豆包使用的 WebSocket PCM relay；OpenAI / Azure Live 在桌面走 WebRTC，Android 没有该传输，因此回退轮流说话。

目标：引入 Android WebRTC 传输层，复用服务端 `/api/live/session` 的 SDP 交换、权限与挂断语义。此项是大改，不能和底层语音整理混在一个 PR。

验证目标：Android 真机完成 OpenAI Live 通话、打断、静音、挂断、后台退出挂断；弱网下回退行为明确。

### P3：手机端凭证 onboarding

现状：密钥写入口已按安全边界收回电脑端。手机只能切引擎，不能配置密钥。

目标：如果手机要成为首次使用入口，需要单独设计凭证 onboarding，而不是重新放开宽泛 `PUT /api/config`。可能方向是电脑扫码确认、一次性授权、或按服务商逐个 narrow write，并保持密钥永不回读。

验证目标：未配对设备、chat-only 设备、旧版本 companion 都无法写入或读取密钥。

## 非目标

- 不让手机直接持有服务商密钥。
- 不把 Live 改成第三方语音代理；机器人仍是 brain，实时语音服务只承担 voice。
- 不在本轮改房间通话；房间仍只走轮流说话。
